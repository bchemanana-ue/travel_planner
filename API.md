# Travel Planner — API Documentation

**Версия API:** 1.0.0  
**Технологии:** FastAPI, Python, SQLAlchemy, PostgreSQL  
**Формат обмена данными:** JSON

## 1. Общая информация

Travel Planner — backend-приложение для планирования коротких путешествий по России продолжительностью от 1 до 3 дней.

Backend предоставляет API для:
- авторизации пользователей через MAX;
- создания и управления поездками;
- получения каталога достопримечательностей;
- добавления мест в маршруты;
- расчёта и хранения бюджета;
- сохранения истории переписки;
- сохранения готовых планов, сформированных AI.

### Базовый адрес

Для локальной разработки:

`http://localhost:8000`

Документация Swagger:

`http://localhost:8000/docs`

Все запросы и ответы с данными используют формат `application/json`.

## 2. Авторизация

Авторизация выполняется через MAX Mini App.

Frontend получает данные авторизации из MAX и передаёт их backend в заголовке:

`X-Max-Init-Data: <initData>`

Backend проверяет подлинность данных, извлекает MAX ID пользователя и находит соответствующую запись в таблице `users`.

Если пользователь обращается впервые, необходимо выполнить авторизацию через `POST /auth/max`. При успешной проверке backend автоматически создаёт пользователя.

### Защищённые запросы

Для всех защищённых эндпоинтов необходимо передавать:

`X-Max-Init-Data: <initData>`

Без этого заголовка запрос возвращает `401 Unauthorized`.

### Роли пользователей

Поддерживаются две роли:
- `user` — обычный пользователь;
- `admin` — администратор.

Администратор имеет право управлять каталогом мест.

Обычный пользователь может просматривать каталог, но не может добавлять, изменять или удалять места.

## 3. Общие служебные эндпоинты

### GET /

Проверка работы приложения.

Ответ:

```json
{
  "message": "Travel Planner работает!"
}
```

### GET /health

Проверка доступности приложения.

Ответ:

```json
{
  "status": "ok"
}
```

### GET /ready

Проверка готовности приложения и подключения к базе данных.

Успешный ответ:

```json
{
  "status": "ready",
  "database": "connected"
}
```

Если база данных недоступна, возвращается HTTP 503.

## 4. Авторизация

### POST /auth/max

Авторизация или регистрация пользователя через MAX.

Заголовок:

`X-Max-Init-Data: <initData>`

Успешный ответ:

```json
{
  "message": "Авторизация прошла успешно",
  "user_id": 1,
  "max_user_id": "123456789",
  "display_name": "Иван Иванов"
}
```

Поля ответа:
- `user_id` — внутренний ID пользователя в базе данных;
- `max_user_id` — идентификатор пользователя MAX;
- `display_name` — отображаемое имя пользователя.

Возможные ошибки:
- `401` — отсутствуют или недействительны данные MAX;
- `500` — не удалось создать пользователя.

## 5. Поездки

Все эндпоинты раздела требуют авторизации.

### GET /trips/

Получение списка поездок текущего пользователя.

Ответ — массив поездок.

### GET /trips/{trip_id}

Получение информации об одной поездке.

Параметр:
- `trip_id` — ID поездки.

Если поездка не найдена или не принадлежит пользователю, возвращается `404`.

### POST /trips/

Создание новой поездки.

Тело запроса:

```json
{
  "title": "Выходные в Казани",
  "destination": "Казань",
  "days": 2
}
```

Поля:
- `title` — название поездки, от 1 до 200 символов;
- `destination` — направление, от 1 до 200 символов;
- `days` — количество дней, от 1 до 3.

Пользователь определяется автоматически по данным MAX.

### PUT /trips/{trip_id}

Полное обновление информации о поездке.

Тело запроса:

```json
{
  "title": "Путешествие в Казань",
  "destination": "Казань",
  "days": 3
}
```

Все поля обязательны.

### DELETE /trips/{trip_id}

Удаление поездки.

При удалении также удаляются связанные места и бюджет. Для сообщений чата связь с поездкой обнуляется.

Успешный ответ:

```json
{
  "message": "Поездка успешно удалена"
}
```

### POST /trips/add-place

Добавление места в поездку.

Тело запроса:

```json
{
  "trip_id": 1,
  "place_id": 2
}
```

Поля:
- `trip_id` — положительный ID поездки;
- `place_id` — положительный ID места.

Возможные ошибки:
- `400` — место уже добавлено в поездку;
- `404` — поездка или место не найдены либо поездка принадлежит другому пользователю;
- `422` — некорректные данные.

### GET /trips/{trip_id}/places

Получение списка мест конкретной поездки.

Доступно только владельцу поездки.

## 6. Каталог мест

### GET /places/

Получение всего каталога мест.

Авторизация не требуется.

### GET /places/{place_id}

Получение информации об одном месте.

Авторизация не требуется.

`place_id` должен быть положительным числом.

Если место не найдено, возвращается `404`.

### POST /places/

Создание нового места.

Требуется роль администратора.

Тело запроса:

```json
{
  "name": "Казанский кремль",
  "description": "Исторический архитектурный комплекс",
  "category": "Достопримечательность",
  "region": "Республика Татарстан",
  "latitude": 55.7986,
  "longitude": 49.1054,
  "average_price": 0
}
```

Поля:
- `name` — название, от 1 до 200 символов;
- `description` — описание, необязательное;
- `category` — категория, от 1 до 100 символов;
- `region` — регион, от 1 до 200 символов;
- `latitude` — широта, необязательная;
- `longitude` — долгота, необязательная;
- `average_price` — средняя стоимость, необязательная, неотрицательная.

### PUT /places/{place_id}

Полное обновление информации о месте.

Тело запроса имеет тот же формат, что и при создании места.

Требуется роль администратора.

### DELETE /places/{place_id}

Удаление места из каталога.

Требуется роль администратора.

Если место используется хотя бы в одной поездке, удаление запрещено.

Возможные ошибки:
- `404` — место не найдено;
- `409` — место используется в поездках;
- `401` — пользователь не авторизован;
- `403` — пользователь не является администратором.

## 7. Бюджеты

Все эндпоинты раздела требуют авторизации.

### POST /budgets/{trip_id}

Создание бюджета поездки.

Тело запроса:

```json
{
  "transport": 2000,
  "accommodation": 4000,
  "food": 1500,
  "activities": 1000
}
```

Все поля необязательны и по умолчанию равны нулю:
- `transport` — транспорт;
- `accommodation` — проживание;
- `food` — питание;
- `activities` — активности.

Все суммы должны быть неотрицательными.

Backend самостоятельно рассчитывает резерв и итоговую стоимость.

Формула:

- промежуточная сумма = транспорт + проживание + питание + активности;
- резерв = 10% от промежуточной суммы;
- итог = промежуточная сумма + резерв.

Передавать `reserve` и `total` в запросе не нужно.

### GET /budgets/{trip_id}

Получение бюджета поездки.

### PUT /budgets/{trip_id}

Полное обновление бюджета поездки.

Формат тела запроса такой же, как при создании.

Резерв и итог пересчитываются автоматически.

### DELETE /budgets/{trip_id}

Удаление бюджета поездки.

Успешный ответ:

```json
{
  "message": "Бюджет успешно удалён"
}
```

### GET /budgets/{trip_id}/places

Получение мест, добавленных в поездку.

Доступно только владельцу поездки.

## 8. Чат

Все эндпоинты требуют авторизации.

### POST /chat/messages

Сохранение сообщения пользователя.

Тело запроса:

```json
{
  "content": "Хочу спланировать поездку в Казань на 2 дня",
  "trip_id": 1
}
```

Поля:
- `content` — текст сообщения, от 1 до 5000 символов;
- `trip_id` — ID поездки или `null`.

Если `trip_id` указан, backend проверяет принадлежность поездки пользователю.

Сообщение сохраняется с ролью `user`.

Пустые сообщения и сообщения из одних пробелов запрещены.

### GET /chat/messages

Получение всей истории переписки текущего пользователя.

### GET /chat/messages?trip_id=1

Получение истории переписки по конкретной поездке.

Сообщения возвращаются в хронологическом порядке.

Если поездка не принадлежит пользователю или не найдена, возвращается `404`.

### Сохранение ответа AI

Внутренняя функция `save_assistant_message()` предназначена для сохранения уже сформированного ответа AI.

Она не является отдельным HTTP-эндпоинтом и не вызывает AI-модель самостоятельно.

Ответ сохраняется с ролью `assistant`.

## 9. Интеграция с AI

### POST /ai/plans

Сохранение готового плана путешествия, сформированного AI.

Требуется авторизация через MAX.

Тело запроса:

```json
{
  "title": "Выходные в Казани",
  "destination": "Казань",
  "days": 2,
  "place_ids": [1, 2, 3],
  "budget": {
    "transport": 2000,
    "accommodation": 4000,
    "food": 1500,
    "activities": 1000
  }
}
```

Поля:
- `title` — название поездки;
- `destination` — направление;
- `days` — количество дней от 1 до 3;
- `place_ids` — список ID мест из каталога;
- `budget` — необязательный объект бюджета.

Если бюджет не передан, поездка сохраняется без бюджета.

Backend проверяет:
- положительность ID мест;
- отсутствие повторяющихся ID;
- существование всех указанных мест.

Затем:
1. Создаёт поездку.
2. Добавляет места в маршрут.
3. При наличии бюджета рассчитывает резерв 10%.
4. Сохраняет поездку, места и бюджет одной транзакцией.

Успешный ответ:

```json
{
  "message": "План путешествия успешно сохранён",
  "trip_id": 5,
  "title": "Выходные в Казани",
  "destination": "Казань",
  "days": 2,
  "place_ids": [1, 2, 3],
  "budget_created": true
}
```

Возможные ошибки:
- `400` — отрицательный ID или повторяющиеся места;
- `401` — пользователь не авторизован;
- `404` — одно из мест не найдено;
- `422` — некорректные данные;
- `500` — ошибка сохранения плана.

**Важно:** данный эндпоинт принимает и сохраняет уже готовый план. Генерация маршрута с помощью AI реализуется отдельно.

## 10. Общие правила валидации

Основные ограничения:
- поездка может длиться от 1 до 3 дней;
- название поездки — от 1 до 200 символов;
- направление — от 1 до 200 символов;
- название места — от 1 до 200 символов;
- категория места — от 1 до 100 символов;
- регион — от 1 до 200 символов;
- сообщение чата — максимум 5000 символов;
- денежные значения не могут быть отрицательными;
- ID поездки и места в соответствующих схемах должны быть положительными.

При ошибке валидации FastAPI возвращает `422 Unprocessable Entity`.

## 11. Коды HTTP-ответов

| Код | Значение |
|---|---|
| `200` | Успешный запрос |
| `201` | Создание ресурса (если настроен соответствующий статус) |
| `400` | Некорректная операция |
| `401` | Пользователь не авторизован |
| `403` | Недостаточно прав |
| `404` | Ресурс не найден |
| `409` | Конфликт, например удаление используемого места |
| `422` | Ошибка валидации данных |
| `500` | Внутренняя ошибка сервера |
| `503` | Приложение не готово или база данных недоступна |

Фактический HTTP-статус зависит от конкретного эндпоинта. В частности, успешные POST-запросы в текущей реализации по умолчанию возвращают `200`, если явно не указан другой статус.

## 12. Безопасность и доступ к данным

- Пользователь определяется по проверенным данным MAX.
- Защищённые запросы требуют `X-Max-Init-Data`.
- Пользователь может работать только со своими поездками.
- Пользователь может просматривать только собственную историю переписки.
- Управление каталогом мест доступно только администратору.
- При ошибках транзакций изменения базы данных откатываются.
- Данные авторизации MAX не следует сохранять в логах или передавать третьим лицам.

## 13. Интеграция frontend и backend

Frontend должен:
1. Получить `initData` через MAX Mini App.
2. Передавать его в заголовке `X-Max-Init-Data`.
3. Отправлять запросы к backend по базовому адресу API.
4. Передавать JSON в теле запросов, где это требуется.
5. Обрабатывать HTTP-ошибки.
6. Использовать ID поездок и мест, возвращаемые backend.

Все URL и параметры запросов приведены относительно базового адреса API.

Для локальной разработки:

`http://localhost:8000`

Swagger UI:

`http://localhost:8000/docs`
